# M3 흐름 설계 — 게시판 · 지도 · 범죄 탐지 · 만남 기록

> 2026-08-18 회의 결과 반영 · 코드 작성 전 흐름 합의용
> 구현 코드는 포함하지 않으며, 무엇을 어떤 순서로 만들지에 대한 기준만 담는다.

## 이번 회의에서 정해진 것

| 항목 | 결정 |
|---|---|
| 발표 방향 | 1·2차와 심사위원이 다르므로 **하나의 완성된 서비스를 처음 소개하듯** 발표 |
| 권한 | 비로그인 = 읽기만 · 로그인 = 쓰기 가능 |
| 게시판 구성 | **A안 확정** — 양육고민 · 동네정보 · 자유수다 · 중고나눔 · 국가지원 · 실종목격 |
| 공략 대상 | 건강관리(55%) · 양육(46%) 두 니즈 |
| 범죄 탐지 | 1번을 확실히, 2~4번은 AI 병행 |

## M3가 하는 일

M1에서 약속이 만들어지고, M2에서 대화와 장소가 연결되었다.
M3는 **만남이 기록으로 남고, 경험이 정보로 쌓이는** 단계다.

```text
발견 → 인사 → 대화 → 약속 → 만남 → 기록 → 정보
                              └──── M3 ────┘
```

# 1. 권한 구조

| 상태 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| **비로그인** | 게시판 읽기 · 지도 보기 · 영상 보기 | 글쓰기 · 댓글 · 채팅 · 반응 |
| **로그인** | 전 기능 | — |

기존 L1·L2 구조를 유지하되, **비로그인 상태에서도 콘텐츠가 보이도록** 한다.
검색 유입과 첫인상을 위해 필요하며, 쓰기 시점에 가입을 유도한다.

---

# 2. 게시판 (양육 공략)

## 2-1. 구성 — A안 확정

| 게시판 | 내용 | 성격 |
|---|---|---|
| **양육고민** | 건강 · 양육 · 훈련 질문 | 묻는 곳 |
| **동네정보** | 병원 · 장소 · 용품 후기 | 알려주는 곳 |
| **자유수다** | 잡담 · 자랑 | 진입 장벽 낮음 |
| **중고나눔** | 사료 · 용품 거래 | 방문 빈도 |
| **국가지원** | 지자체 병원비 · 지원금 · 정책 | 실질 혜택 |
| **실종목격** | 잃어버림 · 발견 | 긴급 |

**양육고민이 가장 중요한 게시판**이다. 견주 수요의 절반 이상이 여기로 오므로
정보 글에 묻히지 않도록 반드시 분리한다.

## 2-2. 도움 표시

경험담을 공유한 사람에게 반응을 남길 수 있게 한다.

```text
글 아래 버튼:  [ 한 수 배웠어요 ]
프로필 표시:   한 수 배웠어요 24
```

| 항목 | 규칙 |
|---|---|
| 대상 | 게시글 · 댓글 |
| 표시 | 누적 횟수 |
| **포인트 · 리워드** | **주지 않는다** |
| **발자국** | **연결하지 않는다** |

### 발자국과 분리하는 이유

| | 발자국 | 도움 표시 |
|---|---|---|
| 의미 | 실제로 만났다 | 글이 도움됐다 |
| 획득 | 오프라인 만남 | 온라인 활동 |
| 검증 | 위치 · 시간 · 양쪽 확인 | 클릭 |

발자국의 가치는 **위조할 수 없다**는 데 있다.
게시판 활동으로 발자국을 주면 집에서 글만 써도 쌓이므로,
"이 사람은 12번 만났다"는 신뢰가 무너진다.

포인트를 주지 않는 이유도 같다. 리워드가 붙으면 서로 눌러주기와 의미 없는 글이 늘어나고,
남은 기간에 어뷰징 방어까지 만들 수 없다. **표시만으로도 인정 욕구는 충족된다.**

## 2-3. 답변자에게 대화 걸기

게시판에서 좋은 답을 준 사람과 **1:1 대화를 열 수 있게** 한다.

```text
답변 아래:  [ 이웃에게 물어보기 ]
              ↓
         1:1 채팅방 생성
```

인사 기능이 이미 있으므로 **진입점만 추가**하면 된다.
이 장치가 있어야 게시판이 관계로 이어지고, "정보로 들어와 관계로 남는" 구조가 실제로 작동한다.

## 2-4. 커뮤니티 대화

게시판 내 실시간 소통은 **기존 오픈채팅방을 사용**한다.
별도 채팅 시스템을 만들지 않는다.

# 3. 지도 (건강관리 공략)

## 3-1. 흐름

```text
[대화]     병원 · 약국 언급
              │
[AI]       최근 3~5줄로 의도 판단 (찾는 중인가)
              │ 예
[프론트]   팝업 → 사용자 클릭 시 위치 권한 요청
              │
[백엔드]   좌표 + 반경으로 장소 검색
              │
[프론트]   지도에 표시
           [ 전화하기 ] [ 약속으로 만들기 ]
```

**"약속으로 만들기"가 핵심이다.** 병원 정보에서 병원 동행 카드로 바로 넘어가면
지도가 서비스의 다른 기능과 연결된다. 정보만 보여주고 끝나면 기존 장소 정보 앱과 다를 것이 없다.

## 3-2. 진료 태그 6종

| 태그 | 값 |
|---|---|
| 진료 시간 | 주간 / 야간 |
| 수술 | 가능 / 불가 |
| 소형견 | 많음 |
| 대형견 | 가능 |
| 주차 | 가능 |
| 친절도 | 상 / 중 / 하 |

**6종으로 고정한다.** 수술 항목을 세분화하면 선택지가 늘어나 아무도 고르지 않는다.
부족하면 데이터가 쌓인 뒤 확장한다.

## 3-3. 병원 후기는 만남과 분리한다

**이 문서에서 가장 중요한 설계 변경이다.**

기존 후기는 만남이 확인된 뒤에만 작성할 수 있다.
그런데 **병원에는 혼자 가는 사람이 압도적으로 많다.**

```text
기존 설계:  병원 동행 약속 → 만남 확인 → 후기 → 태그
현실:       혼자 감 → 후기 못 씀 → 태그 안 쌓임
```

따라서 후기를 두 종류로 나눈다.

| 후기 유형 | 작성 조건 | 발자국 |
|---|---|---|
| 만남 후기 | 만남 확인 필요 | 적립 |
| **병원 후기** | **방문만 하면 작성 가능** | 적립 없음 |

지도에서 병원을 방문한 뒤 **"잘 다녀오셨나요? 경험을 공유해주세요"**로 유도한다.

## 3-4. 데이터 확보 방식

진료 항목은 지도 API가 제공하지 않는다. 공개 데이터셋도 없다.

| 정보 | 확보 |
|---|---|
| 이름 · 주소 · 전화 · 좌표 | 지도 API |
| 야간진료 · 수술 · 친절도 | **사용자 후기** |

병원 제휴는 영업이 필요하고 크롤링은 약관 문제가 있으므로,
**실제 방문자의 후기로 채우는 것이 유일하게 실행 가능한 방법**이다.

초기에는 태그가 비어 있다. 이를 숨기지 말고
**"아직 정보가 없어요. 다녀오시면 알려주세요"**로 안내한다.

## 3-5. 예약 서비스

예약은 병원 쪽 시스템이 있어야 성립한다.

| 단계 | 내용 | 시점 |
|---|---|---|
| 1 | 위치 · 전화번호 표시 | M2 완료 |
| 2 | **전화 걸기 버튼** | **M3** |
| 3 | 후기 태그로 진료 항목 표시 | **M3** |
| 4 | 예약 요청 전달 | 여건이 되면 |

2단계까지가 확실한 범위다. 4단계는 병원 협조 없이 성립하지 않으므로
**여유가 생겼을 때만** 착수한다.

## 3-6. 산책 경로 마킹 — 범위 확인 필요

위치마다 발자국을 남기는 기능은 **실시간 GPS 추적**이 필요하다.
웹 브라우저는 백그라운드에서 위치를 읽지 못하므로
**화면을 켜둔 채 산책해야** 한다.

만남 확인에서 자동 감지를 포기한 것과 같은 제약이다.
**남은 기간에 넣을 항목인지 별도 판단이 필요하다.**

# 5. 범죄 탐지

## 5-1. 대상 4종

10개 유형을 검토한 결과 **금전 사기 계열로 좁혔다.**
발생 가능성이 높고 언어 패턴이 정형적이며 오탐이 상대적으로 적다.

| # | 유형 | 판정 방식 | 우선순위 |
|---|---|---|---|
| **1** | **거절 후 반복 접촉** | **규칙만 (AI 불필요)** | **최우선** |
| 2 | URL · 앱 설치 후 인증 정보 요구 | 규칙 + AI | 다음 |
| 3 | 계좌 · 명의 제공 유도 | 규칙 + AI | 다음 |
| 4 | 유포 협박 · 사칭 + 송금 요구 | AI | 마지막 |

### 제외한 유형과 이유

| 제외 | 이유 |
|---|---|
| 폭력 표현 + 대상 · 시간 · 장소 | 농담과 진심을 언어로 구분 불가. 견주 커뮤니티에서 발생 가능성도 낮음 |
| 미성년 정황 + 만남 요구 | **가입 시 나이를 받지 않아** 판정 근거가 없음 |
| 불법 품목 + 가격 · 수량 | 중고나눔 거래와 구조가 동일해 오탐이 큼 |

미성년 관련은 **나이 수집 여부를 먼저 정해야** 성립한다.

## 5-2. 1번 — 거절 후 반복 접촉 (AI 불필요)

**AI 없이 완결되므로 여기부터 만든다.**

| 판정 기준 | 값 |
|---|---|
| 거절 횟수 | **3회 이상** |
| 재접촉 주기 | 주기적으로 반복 |
| 판정 대상 | 인사 · 채팅 요청 · 친구 요청 |

거절로 보는 신호는 다음과 같다.

- 인사 후 24시간 무응답 (자동 숨김 이력)
- 친구 요청 거절
- 차단
- 채팅방 나가기

**차단 이력과 접근 횟수만 조회하면 되므로** 별도 모델이 필요 없다.

## 5-3. 2~4번 — 규칙 필터 후 AI

```text
메시지 전송
    │
    ├─→ WebSocket ──→ 상대에게 즉시 전달   ← 막지 않는다
    │
    └─→ Kafka ──→ 분석 Consumer
                      │
                   ① 규칙 필터 (계좌·URL·송금 키워드)
                      │ 걸린 것만
                   ② AI 맥락 판단 (앞뒤 대화 포함)
                      │
                   ③ 위험 점수 누적 (사용자 단위)
                      │ 임계값 초과
                   ④ 운영자 검토 큐
                      │
                   사람이 판단 → 조치
```

**채팅을 막지 않는다.** 분석이 얼마나 걸리든 대화는 그대로 흐르며,
정상 사용자는 이 기능의 존재를 알지 못한다.

## 5-4. 누적이 핵심이다

한 번의 메시지로 판단하지 않는다.

| 조건 | 처리 |
|---|---|
| 1회 감지 | 기록만 |
| 여러 상대에게 반복 | 위험 점수 누적 |
| 임계값 초과 | 운영자 검토 큐 |

**같은 사람이 여러 명에게 같은 패턴을 쓰는 것**이 가장 강한 신호다.
누적이 있어야 오탐도 줄어든다.

## 5-5. 오탐이 많으면 기능이 죽는다

운영자 검토가 있다는 사실이 오탐을 정당화하지 못한다.

| 하루 알림 건수 | 결과 |
|---|---|
| 5건 | 검토 가능 |
| 200건 | **방치됨** |

**임계값을 높게 잡아 적게 올리는 편이** 낫다.

## 5-6. 지켜야 할 원칙

| # | 원칙 | 이유 |
|---|---|---|
| 1 | **자동 제재 없음** | 오판 시 무고한 사용자가 막힌다 |
| 2 | **대화 원문 미저장** | 위험 신호와 시각만 남긴다 |
| 3 | **사용자 고지** | 약관 · 온보딩에 분석 가능성을 명시 |
| 4 | **상시 감시 아님** | 규칙에 걸린 것만 AI로 보낸다 |

3번은 **기능보다 먼저** 처리한다.

## 5-7. 운영자 화면

**관리자 대시보드에 붙인다.** 별도 개발을 줄일 수 있다.

| 요소 | 내용 |
|---|---|
| 대상 사용자 | 누적 점수 · 감지 횟수 |
| 감지 이력 | 유형 · 시각 · 위험도 |
| 대화 조회 | 필요 시에만. **조회 자체를 로그로 남긴다** |
| 조치 | 경고 · 일시 정지 · 해제 |

# 6. 만남 기록 — 코인사 · 발자국

## 6-1. 흐름

```text
약속 시각 도래
      │
각자 앱을 열고 "만났어요" 클릭
      │
프론트가 이때 위치 권한 요청 → 좌표 1회 읽음
      │
백엔드가 대조
  · 반경 100m 이내
  · 약속 시각 ±1시간
  · 양쪽 모두 확인
      │
만남 확인 성립 → 후기 화면
      │
장소 태그 + 한 줄 후기(선택)
      │
발자국 적립 · 장소 정보 갱신
```

## 6-2. 판정 기준

| 항목 | 값 |
|---|---|
| 근접 반경 | 100m |
| 시간 창 | 약속 시각 ±1시간 |
| 성립 조건 | 양쪽 모두 확인 |
| 위치 정확도 | 50m 이상이면 안내 |

반경을 좁게 잡으면 **실제로 만났는데 확인되지 않는** 문제가 생기고 이는 이탈로 이어진다.
넓게 잡아 생기는 오차는 양쪽 확인 규칙으로 흡수된다.

## 6-3. 위치가 부정확할 때 — 확인 코드

```text
위치 정확도 50m 이상
      │
한 사람 화면에 4자리 숫자 표시
      │
상대가 입력 → 일치하면 성립
```

**눈앞에 있어야만 가능**하므로 위치 조작이 무의미해진다는 장점도 있다.

## 6-4. 후기와 발자국

| 항목 | 규칙 |
|---|---|
| 별점 | 두지 않는다 |
| 건너뛰기 | 허용. 만남 기록은 남고 발자국만 미적립 |
| 발자국 적립 | 후기 제출 시점. 같은 상대와는 하루 1개 |
| 공개 | 작성자 비표시. 집계 형태로만 장소 정보에 반영 |

발자국은 순위나 보상과 연결하지 않으며 총수를 타인에게 표시하지 않는다.
노쇼는 감점하지 않고 발자국이 적립되지 않을 뿐이다.

### 평가 점수를 두지 않는 이유

사람을 점수로 매기면 낮은 사람이 배제되고, 오프라인 만남 서비스에서는 그 피해가 더 크다.
심사에서 지적이 나오면 **만들지 못한 것이 아니라 만들지 않기로 한 것**임을 설계 근거와 함께 설명한다.

# 7. 진행 순서

| 순위 | 항목 | 규모 | 비고 |
|---|---|---|---|
| **1** | 코인사 + 발자국 + 만남 후기 | 중 | 루프를 닫는 유일한 작업 |
| **2** | 게시판 6종 + 도움 표시 | 중 | 양육 니즈 공략 |
| **3** | 병원 후기 + 진료 태그 6종 | 소 | 1번에 붙으면 거의 공짜 |
| **4** | 범죄 탐지 1번 (거절 후 반복) | 소 | **AI 불필요** |
| 5 | 답변자에게 대화 걸기 | 소 | 진입점만 추가 |
| 6 | 채팅 사진 · 공유 버튼 | 소 | |
| 7 | 범죄 탐지 2~4번 | 중 | 규칙 필터부터 |
| 8 | 산책 경로 마킹 | 대 | **범위 판단 필요** |
| 9 | 예약 요청 전달 | 대 | 여건이 될 때만 |

**1~4번이 M3의 필수선**이다. 5번 이하는 여유에 따라 조정한다.

# 9. 발표 관점

심사위원이 1·2차와 다르므로 **하나의 완성된 서비스를 처음 소개하듯** 구성한다.

## 서사

> 열 가구 중 세 가구가 반려동물을 키우고, 그중 여덟이 개입니다.
> 이들이 가장 궁금해하는 건 **건강과 양육**입니다.
> 매일 마주치지만 서로 모르고, 대화는 "언제 한번"에서 멈춥니다.
>
> 같이놀개는 그 대화에서 **약속을 꺼내고**, 만나면 **기록으로 남기고**,
> 그 기록이 **다음 사람의 정보**가 되게 합니다.

## 표현 주의

| 피할 표현 | 대신 |
|---|---|
| AI가 범죄를 잡아냅니다 | AI는 **검토 대상을 좁혀 운영자에게 전달**합니다 |
| 대화를 실시간 감시합니다 | 규칙에 걸린 경우에만 분석합니다 |
| 건강 정보를 제공합니다 | **물어볼 이웃**을 만들어줍니다 |

## 완료 기준

한 사용자가 다음 흐름을 **끊김 없이 이동**하면 M3 통과다.

```text
가입 → 인사 → 대화 → 약속 → 만남 확인 → 후기 → 발자국
```

기능 개수가 아니라 **이 한 줄의 완결성**이 발표의 성패를 가른다.
